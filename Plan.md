# План проверки и автоматизации приложения «Мобильный хоспис»

**Приложение:** «Мобильный хоспис» (отображаемое имя — «В Хосписе»)  
**Пакет:** `ru.edu.qamid`  
**Платформа:** Android API 36  
**Бэкенд:** `https://students.netoservices.ru/qamid-diplom-backend/`  
**Учётная запись для прогона:** `login2` / `password2`

---

## 1. Объект и объём проверки

Клиентское Android-приложение: новости хосписа, панель администратора, экран «Наша миссия».

| Модуль | Что проверяем |
| --- | --- |
| Splash-экран | Изображение, цитата, индикатор, переход на авторизацию или Главную |
| Авторизация | Поля, валидация, успешный вход, ошибки, отсутствие сети, сессия |
| Главная | Блок «Новости» (не больше 3 карточек), раскрытие, «Все новости», pull-to-refresh, меню |
| Список новостей | Активные новости, раскрытие, сортировка, фильтр, панель управления |
| Фильтрация | Категория, период дат, статус (в панели), валидация, отмена |
| Панель управления | CRUD, сортировка, фильтр, удаление |
| Создание / редактирование | Поля, дата и время, активность, отмена |
| Наша миссия | 8 цитат, раскрытие текста |
| Навигация и сессия | Меню, миссия, выход, повторный вход |

**Вне объёма:** заявки, документы, регистрация, смена пароля, веб и iOS; нагрузочное и пентест. Внутренности Room / Hilt / Retrofit отдельно не тестируем.

---

## 2. Схема экранов

```
Splash → Auth → Main ↔ NewsList ↔ FilterNews
              Main / NewsList / Panel → OurMission
              NewsList (admin) → NewsControlPanel → CreateEditNews
```

На Главной и в публичном списке — только активные новости с датой публикации не позже текущего момента; на Главной не больше 3 карточек. Проверка в портретной ориентации.

## 3. Типы тестирования

| Тип | Что проверяем |
| --- | --- |
| Функциональное | Вход, новости, CRUD, фильтры, цитаты |
| UI | Состав экранов, подписи, AppBar, карточки |
| Негативное | Пустые поля, неверные данные, отмена в диалогах |
| Навигация | Splash, меню, выход, цепочки экранов |
| Валидация | Обязательные поля, период дат, DatePicker |
| Роли | Панель управления для администратора |
| Сеть и ошибки | Нет сети, сбой загрузки, пустые списки |

## 7. План автоматизации UI-тестов

**59** тест-кейсов; к автоматизации **55** («Да»), **4** («Нет»):

- TC-05 Вход без сети: Нельзя надёжно управлять сетью эмулятора из UI-теста.
- TC-15 Отказ в панели управления без прав администратора: Нет второй учётной записи без прав администратора.
- TC-27 Splash показывает тематическую цитату: Картинка и цитата splash выбираются случайно; нельзя зафиксировать конкретный текст.
- TC-39 Ошибка загрузки списка новостей: Без мока бэкенда ошибку сервера нельзя вызвать стабильно.

Кейсы с известными дефектами приложения (TC-04, TC-34 и др.) на этапе 2 оформляются как ожидаемое поведение: падение теста фиксируется в Allure; это отразить в `README.md` и `Result.md`.

**Инструменты и практики:** Espresso, Page Object, Allure (`@Epic`, `@Feature`, step, скриншот при падении). Код тестов: `app/src/androidTest/java/ru/edu/qamid/...`. Тесты независимы: `@Before` — сброс на экран авторизации. Ожидания (`IdlingResource`, `waitFor`) вместо `Thread.sleep`. После сценариев с `QA_` — удаление созданных новостей. В `gradle.properties`: `android.injected.androidTest.leaveApksInstalledAfterRun=true`.

Пункты **P2** без отдельного кейса: CL-01.06, CL-02.03, CL-02.11, CL-03.09, CL-04.09, CL-05.12, CL-06.11, CL-06.12, CL-07.03, CL-07.09, CL-07.17, CL-08.06.

## 8. Ограничения и риски

- Общий бэкенд — изменяемый состав списков новостей.
- Случайная цитата на splash — автотест не привязывать к конкретному тексту (TC-27).
- Одна учётная запись и отсутствие неактивных новостей без `QA_Inactive` — часть пунктов «Неприменимо».
